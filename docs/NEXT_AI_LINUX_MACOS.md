## Backend Linux : critères précis

- Source audio prioritaire : **graphe PipeWire réel**, via une API compatible avec la version installée (`libpipewire`/bindings ou client maintenu). Identifier les nœuds de capture, leur état de flux et leurs liens avec une source audio. Lire `application.process.id` / propriétés de processus lorsqu'elles existent et vérifier l'identité avec `/proc/<pid>/stat` (temps de démarrage), `/proc/<pid>/exe` et, si autorisé, UID et nom. Prévoir un identifiant stable **PID + heure de création**, sans supposer qu'un PID seul est une instance. Vérifier sur la version PipeWire effectivement testée le sens des ports et des liens, plutôt que coder une orientation présumée.
- Vidéo : rapprocher les nœuds PipeWire vidéo et `/dev/video*` / V4L2 ; ne déclarer `Active` que si des données observables confirment un flux en cours et permettent d'identifier sa ressource et son processus. Un FD ouvert vers `/dev/video*`, un nœud installé ou une permission de portail ne prouvent **pas** un flux : au mieux `Ready` avec `Confidence::Low` et une preuve explicite. Si une capture contourne PipeWire via V4L2 direct et qu'aucun signal de streaming fiable n'est disponible sans privilèges, indiquer `degraded` ou `unavailable` pour l'activité vidéo et expliquer la limite dans `doctor` ; ne pas convertir un FD en `Active`.
- Gérer l'absence de serveur PipeWire, les permissions `/proc`, les redémarrages serveur, la déconnexion USB et la réutilisation d'un PID : un collecteur inaccessible doit émettre une santé `Degraded`/`Unavailable` documentée, **pas** un instantané vide marqué sain. Pas de polling qui accumule des clients, FD ou processus ; arrêter proprement `watch`.
- Vérification demandée sur **un hôte Linux avec PipeWire et périphériques** : microphone inactif → flux micro réel → arrêt ; caméra inactive → capture vidéo réelle → arrêt ; application à capture ouverte mais inactive ; débranchement/rebranchement ; PipeWire arrêté ; permissions refusées. Observer les transitions de `mcw watch --json`, l'attribution PID et le résultat de `mcw doctor`. CI `ubuntu-latest` pour `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`, `cargo build --release`, plus tests de parsing/états isolés. Un runner sans périphérique ne remplace pas le smoke matériel.

## Backend macOS : capacités vérifiées et limites

- Cibler **macOS 15+** si l'implémentation s'appuie sur les nouvelles propriétés `AudioHardwareSystem.processes`, `AudioHardwareProcess.isRunningInput` et `pid` (Apple documente ces propriétés comme disponibles depuis macOS 15). `isRunningInput == true` signifie qu'au moins un flux d'entrée audio du processus est actif. Énumérer les processus CoreAudio, lire PID et bundle ID, gérer les erreurs de permission ; attribuer l'activité micro seulement si la propriété est observée. Ne pas confondre appareil audio présent, permission TCC et capture active. Un helper Swift natif compilé et distribué avec l'outil ou un binding Rust maintenable sont possibles ; ne pas dépendre d'un script absent au runtime.
- Pour la caméra, `AVCaptureDevice.isInUseByAnotherApplication` indique qu'**une autre** application utilise le périphérique ; cette propriété ne livre pas l'identité du processus. Si elle est fiable dans le scénario testé, émettre une observation par périphérique avec `pid: null`, une application explicitement inconnue, `EnforcementDecision::Unknown` et preuve sourcée ; aucun nom/PID inventé. Si son comportement reste non vérifié (permissions TCC, caméra virtuelle, partage multi-apps), marquer ce collecteur dégradé plutôt que prétendre à l'attribution. Ne pas accéder à la caméra pour fabriquer une activité ni contourner TCC.
- Ajouter CI `macos-latest` pour compilation/tests et, lorsque possible, un exécutable de test natif. Tester sur un **Mac doté d'un micro et d'une caméra** : activité micro vraie/fausse avec PID, usage de caméra par une autre application, arrêt, absence de périphérique et permission refusée. Sans ce Mac, documenter explicitement quelles parties restent non vérifiées ; pas de promesse de blocage caméra global, d'icône menu bar ou de binaire macOS « prêt » sans implémentation réelle.
- Sources Apple à consulter avant codage : [processes](https://developer.apple.com/documentation/coreaudio/audiohardwaresystem/processes), [isRunningInput](https://developer.apple.com/documentation/coreaudio/audiohardwareprocess/isrunninginput), [pid](https://developer.apple.com/documentation/coreaudio/audiohardwareprocess/pid), [isInUseByAnotherApplication](https://developer.apple.com/documentation/avfoundation/avcapturedevice/isinusebyanotherapplication). Vérifier les disponibilités dans le SDK utilisé.
