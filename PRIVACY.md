# Privacy Policy

**MicCamWatch** (`mcw`) is an open-source, offline-first security and privacy monitor for Windows, Linux and macOS. Controls have explicit platform scopes: Windows device administration, Linux PipeWire-session source mute and optional administrator-authorized USB webcam controls, and macOS writable INPUT mute/manual Restrictions profiles. None is advertised as a universal hardware kill-switch.

## Data Collection and Storage

- **Offline by default, not zero data processing**: The reviewed monitoring paths contain no project-directed automatic uploader for observations, activity history, analytics or crash reports. Explicit installation/update contacts GitHub for installer/release metadata, archives and checksums; Windows portable uninstall can also fetch the matching release when its ownership receipt is absent. Those download calls do not attach monitoring history or policy files. With `trust_policy = "offline"`, Windows forbids online chain/revocation retrieval, macOS uses Security.framework's no-network validation flag, and Linux disables GnuPG automatic key retrieval/import and WKD lookup. Explicit `"online"` permits native certificate/revocation or configured keyserver work during observation; recipients can learn the requested certificate/key, connection IP and timing. This trust setting does not control all OS, antivirus, proxy, DNS, backup, filesystem or package-manager networking. macOS best-attempt revocation is not proof of a fresh response, Gatekeeper/notarization or an antivirus verdict.
- **No Audio or Video Recording**: MicCamWatch never records audio streams, captures webcam frames, or inspects media payloads. It only reads OS-level metadata:
  - Windows Core Audio / WASAPI session information (PID, session state, capture device name).
  - Windows Capability Access Manager registry timestamps (`LastUsedTimeStart`, `LastUsedTimeStop`).
  - Windows Media Foundation sensor process-activity/streaming-state metadata; an active stream without a validated PID remains unattributed.
  - Loaded DLL modules associated with capture frameworks (DirectShow, Media Foundation) to correlate capability.
  - Process metadata (PID, executable path, process tree ancestry, Authenticode digital signatures) to identify which application accessed the device.
  - Depending on the platform, account/domain names or numeric UIDs, session/integrity context, process instance identities and ancestry timestamps can identify a person or environment. Some Windows checks inspect command lines in memory; raw command lines are not dedicated serialized activity-event fields.
  - Linux PipeWire graph metadata, authenticated client/process identity, `/proc` metadata and V4L2 device inventory/open-handle observations.
  - macOS CoreAudio process input-activity metadata, AVFoundation device inventory, public CoreMediaIO camera device running-state and process identity from `libproc`. Camera client/PID stays unknown; running-state does not prove frame flow. The embedded native helper does not start a media capture session or request camera permission.
- **Local Storage**: Common Windows user-data locations are listed below; privileged control records can also be outside the user profile:
  - Settings: `%APPDATA%\MicCamWatch\settings.toml`
  - Activity history: `%LOCALAPPDATA%\MicCamWatch\history.jsonl`, **enabled by default** where the frontend records events. Rotation occurs when the current file is already at least 5 MiB before the next append, with three backups; there is no age-based expiry or strict total-size cap. `mcw history clear` removes these four history files, not future recording, selected logs, OS logs or control journals; disabling history does not erase existing files.
  - Camera block state: `%LOCALAPPDATA%\MicCamWatch\blocked-camera-devices.json`
  - Optional `mcw watch --log` writes to the path you choose; `--eventlog` delivers local Windows Event Log, Linux syslog/journal, or macOS unified-log entries. OS logging retention/access rules are outside MCW's history settings.
  - Windows control state also includes per-user microphone-protection intent and protected camera journals under `%ProgramData%\MicCamWatch\CameraGuard`; these are not activity history and have no general age-based purge.
- **Unix Local Storage and Installation**: Settings, policy, rotating history, control-ownership journals, autostart receipts and local tray IPC metadata use per-user XDG/HOME locations. Linux microphone restoration uses `$XDG_STATE_HOME/miccamwatch` or `$HOME/.local/state/miccamwatch`. The user installer defaults to `$HOME/.local/bin` with installation/PATH ownership receipts, without implicit autostart or device action. Ordinary user uninstall preserves personal settings, policy, history and control data; pending protection/restoration must be resolved through the appropriate explicit procedure. The native managed-uninstall path and standalone installer have different cooperative-stop/running-target rules.
- **macOS Temporary Processing**: Native helper observations and error responses pass through private temporary files even with history disabled. Normal cleanup removes request files and owned helper material when safe; interrupted processes can leave files, and possibly running helper bundles are deliberately preserved. These files contain metadata/diagnostics, not media recordings.
- **Linux Administrator Camera State**: Optional USB webcam controls require a separately reviewed, matching root helper and explicit Polkit administrator authorization. `/var/lib/miccamwatch` stores a root-only restoration journal and installation receipt plus a locally readable status cache containing owned USB identities (boot, topology, descriptors and optional serial), authorizing caller UID, original driver bindings and operation state; no media or network upload. Actions target only admitted UVC video interfaces, not separate audio/storage interfaces, non-USB cameras or global driver modules. No automatic hotplug or camera-on-lock action is performed. Restore owned bindings and explicitly uninstall the root component before an ordinary user update/removal; install the new matching root component separately afterward. Removal refuses pending/malformed restoration evidence and preserves the permanent operation lock.
- **macOS Helper Identity**: Embedded public-framework code runs in a private, per-user helper `.app` with a stable application identifier. Local ad-hoc signing supports that application identity; it is not Apple Developer ID, notarization or a trusted publisher claim. Cleanup removes only owned helper material and preserves bundles still in use. Native notification authorization and manual camera-profile installation/removal remain user-controlled.
- **Scoped Privacy Controls**: Windows camera actions use native SetupAPI/Configuration Manager operations through a separately approved elevated coordinator (UAC). Linux microphone changes affect only sources in the accessible PipeWire session, never global ALSA policy; optional USB camera actions use the separate root/Polkit component described above, never permission-only V4L2 denial. macOS changes only exposed writable INPUT CoreAudio mute properties. Owned restoration preserves previously muted sources and retains unavailable-device work for a later retry. A macOS camera restriction is a manually approved profile identified by an owned UUID; installed payload metadata is profile evidence, not physical capture-denial proof. External profiles are never removed. Public macOS lock state remains Unknown, and lock-policy enable is refused.
- **Local Background Monitoring**: Windows uses its windowless tray; Linux requires an actual StatusNotifier host and session notification service; macOS uses its native AppKit menu bar. These observe metadata and optionally retain history/deliver alerts. Windows lifecycle uses local window messages; Unix lifecycle uses private same-user local IPC. No remote tray service is used. Explicit autostart consent creates an owned per-user Windows registration, Linux desktop entry, or macOS LaunchAgent; updates never silently enable an absent/disabled/unmanaged registration.

## Website Processing and Publication Review

The prepared website-policy target is <https://miccamwatch.pages.dev/privacy>, with seven localized variants. **This draft has not been deployed or approved for publication.** The source metadata is `site/privacy.json`; its private contact email remains `null` pending confirmation.

The website and the application must not be conflated. Cloudflare Pages receives ordinary request metadata for hosting/security. The public response examined on **2026-10-23** injected Cloudflare Web Analytics, but its external script was actually blocked by the delivered CSP in the browser check. Responses also advertised Cloudflare NEL, which can cause compatible browsers to report network failures. This is not MCW activity-history or crash-report upload. The site's own JavaScript has no cookie or Web Storage persistence; no cookies/storage entries were observed in that check, not a universal provider guarantee.

Cloudflare's [privacy policy](https://www.cloudflare.com/privacypolicy/), [NEL documentation](https://developers.cloudflare.com/network-error-logging/) and [Web Analytics retention documentation](https://developers.cloudflare.com/web-analytics/faq/), and [GitHub's privacy statement](https://docs.github.com/en/site-policy/privacy-policies/github-general-privacy-statement), describe their respective purposes, retention criteria and international-processing safeguards. NEL browser-policy lifetime is not log retention; Web Analytics retention is not a blanket hosting-log deadline.

Before publication, confirm the operator/controller identity and role, supply a private privacy email, validate the proposed legal bases and actual hosting arrangements, and establish any private-correspondence retention criteria. Replace the draft/proposal wording consistently in all languages after those confirmations. No company, DPO, address, specific provider-log deletion period or GDPR certification is invented. Deployment still requires the user's explicit approval, followed by an actual HTTPS check of the public policy URL; local-preview success is not proof that Microsoft has fetched it.
